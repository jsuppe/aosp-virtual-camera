# Ranked areas for latency/throughput investigation

GPU service, queue waiting, CPU scheduling and photon presentation are different endpoints. Do not sum overlapping stage medians. Track frame/configuration identity through each stage, and report fresh pixels separately from successful Camera2 callbacks.

- **1. Camera HAL / GLES destination handling — confirmed work; current experiment.** `hal/core/GpuCompositor.cpp::composite` imports images, attaches an output renderbuffer, draws a full-screen quad and creates a completion fence. This is a real full-frame pass, not only queueing. Test clear/discard before complete overwrite to avoid loading old destination tiles. Keep source/destination acquire fences, cancellation and release-fence ownership intact. Pixel-correctness qualification is required before enabling an optimization by default.
- **2. Producer app / Skia / Android RenderThread — confirmed substantial work.** Procedural scene rendering, direct-mirror rendering and clock-overlay creation are additional jobs; the left pane is still a TextureView. Measure each with native GPU attribution and CPU substage timings. Test a simpler scene, GPU-native clock overlay, shared rendered content instead of rendering twice, and left-pane SurfaceView independently. Avoid changing several variables in one comparison.
- **3. Gralloc / minigbm / Mesa allocation — confirmed layout change.** SurfaceView compositor usage currently follows the legacy scanout path, changing UIF-tiled output into linear output. Investigate format/modifier negotiation shared by renderer and display; query actual KMS plane `IN_FORMATS` support first. Do not strip compositor usage or force UIF into a buffer that display hardware cannot scan out. Compare same-format/layout-only GPU microbenchmarks before assigning the entire delta to layout.
- **4. Mesa V3D driver / GPU memory traffic — candidate mechanism behind measured GPU cost.** Inspect tile loads/stores, texture reads, cache behavior, resolve/copy work and tile configuration using GPU performance counters. The HAL reimports EGLImages/renderbuffers per output frame; separately measure CPU/import cost and investigate lifetime-safe per-buffer caching. A faster GL API call is not proof of shorter GPU service. Driver changes require matched-driver A/B and regression coverage.
- **5. Camera framework / BufferQueue / producer-HAL handoff — queue-latency candidate.** Measure producer queue depth, source freshness, destination dequeue waits, pending camera requests and fence readiness for each identified frame. Larger queues can improve apparent throughput while adding latency. Test a promptly drained non-displaying consumer to separate camera transport from UI/composition. Buffer ownership redesign for zero-copy is larger work, not a flag toggle.
- **6. HAL fence waits / pacing — measured secondary cost in earlier traces.** Compare fence signal timestamp with wakeup/observation and result completion. Investigate cancellable event-driven waits instead of polling where the existing path polls. Do not bypass GPU dependencies, reuse buffers early, or lengthen deadlines and call that an optimization. Preserve stream reconfiguration and teardown safety.
- **7. SurfaceFlinger / HWComposer — presentation/composition target.** Trace buffer readiness→latch→composition→present fence, confirm DEVICE versus CLIENT per layer, and inspect fallback when scaling, overlays or capture are active. The right SurfaceView was DEVICE-composed in current evidence; the left TextureView still causes app rendering. `drm_hwcomposer` plane format checks and modifier-aware framebuffer import/atomic TEST_ONLY paths are relevant places to inspect, not evidence that HWC is currently doing an extra GPU copy.
- **8. DRM/KMS / display controller / monitor — physical latency target.** Verify actual active120Hz mode, plane format/modifier/scaling constraints, atomic commit and page-flip timing, in/out fences, missed vblanks and scanout position. A120Hz frame interval is8.33ms; readiness relative to latch/scanout matters. Direct scanout does not imply zero latency. Use present fences plus an optical/high-speed-camera test for photon latency, not only matching on-screen numbers. KMS has not been modified by these experiments.
- **9. Kernel CPU/GPU scheduling / DVFS / memory bandwidth — conditional target, not established primary cause.** Correlate scheduler wakeups, preemption, GPU job queue depth, IRQ service, GPU/CPU clocks, temperature and bandwidth counters with the slow frames. Current repeat samples show near1GHz GPU clocks and the pass difference even without saturation at60fps; no evidence for a twofold clock loss. Measure before touching governors, priority, affinity or kernel scheduling. Sustained thermal tests remain separate.
- **10. Logging / screen capture / diagnostics — intermittent-jank target.** Heavy115200-baud kernel-console printing can perturb timing, while an idle enabled console does not explain the observed doubling. Serial windows were mostly silent in the allocation experiment. Compare ordinary use with recording/scrcpy and diagnostic overlays disabled; avoid readback/encoding during baseline traces. Keep debug safety while measuring logging bursts.

## Execution priority

First the clear-before-overwrite control, then pixel-correctness qualification if promising. Next remove duplicated producer/left-preview work and measure a non-displaying consumer. Pursue allocator/Mesa/HWC/KMS modifier negotiation only with advertised hardware capabilities and a controlled layout benchmark. Kernel/governor changes are not the first lever given current GPU evidence.

## Scope

No permanent AOSP framework, kernel, KMS, HWC, allocator or Mesa changes were installed for these investigations. Temporary HAL profiling overlays are restored; the previously delivered SurfaceView app remains. The broad list is a ranked investigation map, not a claim that every subsystem is causing the current latency.
